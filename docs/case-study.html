01Problem

Stop checking multiple websites for Berlin WBS apartments.

New listings can appear and disappear quickly. Checking several housing-provider websites again and again takes time, repeats the same work and makes it easy to see a suitable apartment too late. FlatFeed lets users save four criteria once and receive a Telegram notification when a matching Berlin apartment appears.

Product in one sentence

One saved WBS filter replaces repeated checks across provider websites and turns new matching listings into timely Telegram alerts.

WBS (Wohnberechtigungsschein) is a certificate used to qualify for subsidized housing in Berlin. Kaltmiete is base rent, excluding operating and heating costs.

02Solution

One saved filter turns repeated website checks into timely Telegram alerts.

Users set WBS type, district, maximum Kaltmiete and rooms once. FlatFeed prepares listings from different sources in one format, applies fixed matching rules and notifies the user when a newly collected apartment matches the saved criteria.

04My Role

I owned the product decisions from problem definition to evaluated prototype.

This was a self-directed portfolio project. I owned the product, evaluation and implementation decisions directly rather than managing an ML team or a live rollout.

My contribution

I defined the WBS user problem and product scope. I made timely notifications part of the core flow because repeatedly monitoring several sites takes time and a late discovery can leave too little time to respond. I chose the four matching fields, shaped the shared source-adapter architecture, set the boundary between fixed rules and AI, and designed the evaluation plan and acceptance criteria. I implemented the Telegram prototype with Claude Code and Codex as coding collaborators.

05How AI Fits

AI checks data quality without deciding which apartments users see.

WBS type, district, maximum Kaltmiete and rooms are explicit criteria, so matching does not need a model. AI is useful as a second quality check because housing providers can describe the same listing details in different language and layouts.

A

Fixed rules match listings

Deterministic code compares every listing with the saved filter, so the same inputs always produce the same result.

B

AI checks the parser

AI rereads the original listing text and extracts exact source evidence for values that may have been parsed incorrectly.

C

Admins review discrepancies

AI can create a private review task. It cannot change a listing, decide whether it matches or edit a Telegram card.

Product boundary

The user path and the admin quality path stay separate.

For users

FlatFeed compares each listing with the saved filter and sends matching apartments in one consistent Telegram format.

For admins

AI can point to a possible parsing discrepancy for review. Fixed code still owns listing data and matching.

How I selected the setup

I increased model capability only when the previous setup missed a predefined gate.

I started with lower-cost settings and moved to a stronger configuration only when the previous one missed acceptance criteria defined before the run.

  1. 01 Start with lower-cost settings

    I began with gpt-5.6-Luna and compared no additional reasoning with low reasoning effort.

  2. 02 Increase capability with evidence

    When Luna missed the gates, I moved to gpt-5.6-Terra and compared none, low, medium and high reasoning effort on new datasets.

  3. 03 Narrow the AI’s job

    More model power alone was not enough. I limited AI to extracting exact source quotes and let fixed code compare them. The final Terra-high setup met every predefined gate.

AI QA evaluation · synthetic data · 600 listings

Can AI catch parser errors before admins rely on the data?

Parsing and matching stay rule-based. I tested AI only as a second quality check for admins. The model reread the original listing and returned exact source quotes; fixed code compared them with the parsed values. The final test used 600 synthetic listings: 300 clean listings and 300 listings containing one planted parser error.

Decision

Passed the synthetic benchmark. The checker found all 300 planted errors, raised no false alerts on 300 clean listings and returned a usable result for 599 of 600 checks. Every predeclared prototype target passed.

What did not work

One clean listing produced no usable result.

The model returned a quote that did not appear exactly in the raw listing text, so local validation rejected it. The check was not retried and did not create a false alert. It was the only unusable result; no planted parser error was missed.

How the final check worked

AI read the source. Code made the decision.

The final configuration used gpt-5.6-Terra with high reasoning effort and strict structured outputs. The model read the original listing text and returned quoted evidence for eight listing values. Fixed code compared that evidence with FlatFeed’s parsed data. If the two differed, it created one admin task: review_required. This experiment ran offline and is not integrated into the product. It is separate from runtime AI QA and cannot change a listing, decide a match or edit a Telegram card.

I ran the final 600-listing benchmark once within the planned budget and did not tune the result afterwards.

The final run met every synthetic acceptance gate, so I stopped synthetic tuning. The prototype is complete at its intended scope: an implemented Telegram flow, deterministic matching and a bounded AI quality-control role. Performance on live provider data still needs separate validation.

07What I Learned

A stronger model helped. A narrower AI task made the result reliable.

The most important lesson was not to make AI responsible for more of the product. It was to give AI one uncertain task and keep the final comparison deterministic.

A

Rules are better for explicit criteria

WBS type, district, rent and rooms do not need model judgment. Fixed matching is cheaper, traceable and predictable.

B

Model power was only part of the answer

The accepted result required both a stronger configuration and a narrower task: extract evidence, then let code compare it.

C

Synthetic success has a clear limit

The benchmark shows controlled feasibility. It does not prove live-source coverage, natural parser-error rates or user impact.

What I would test next

I would validate permitted live-source access and alert usefulness before expanding the AI system. The next product evidence should measure source coverage, time from a listing appearing to an alert being delivered, acted-on notifications and the rate of irrelevant or unavailable matches. The next major question is whether FlatFeed helps users find suitable listings faster, not whether a larger model can improve a synthetic benchmark.

Current limits

The capabilities are implemented, but the demo runs in a controlled setup.

Demo configuration

  • The multi-source ingestion layer is implemented, but only the FlatFeed Synthetic adapter is enabled. The demo does not scrape housing-provider websites.
  • Users can request matches on demand. Automatic notifications work when BOT_BACKGROUND_ENABLED=true; this demo keeps the switch off.
  • Runtime AI QA for admins is implemented but disabled. The accepted model configuration was evaluated offline, is not part of the user-facing product flow and is not connected to Telegram.
  • The showcase photo, address, district and coordinates refer to Schlangenbader Straße 91. The building photo is by Bodo Kubrak, CC0 1.0, and the local copy was resized. Availability, rent, floor, rooms and WBS eligibility are synthetic.

Still needs real-world validation

  • Whether real Berlin WBS users adopt and trust the product
  • How complete and up to date permitted housing-provider sources would be
  • Parser accuracy on real source formats and naturally occurring errors
  • Whether the product reduces monitoring time and helps users respond faster
  • Before production, human reviewers would still check every AI alert and a random sample of listings without alerts

Case study summary

One filter. Timely apartment alerts. FlatFeed brings multiple listing sources into one flow, matches apartments with fixed rules and uses AI to check data quality.
